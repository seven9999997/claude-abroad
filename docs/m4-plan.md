## 0. 总原则

### 0.1 会话里能做什么

宿主机唯一的禁区是断网（CLAUDE.md）。M4 的大部分工作在虚拟机里或纯计算：

- **纯计算和进程内测试**：出口变化规则、闸门状态机、地区映射、环境检测各项的判定、命令拼装和输出解析。时钟、进程表、命令执行器、HTTP 查询源都可注入。
- **真实虚拟机**：命名空间、veth、nft、WireGuard、OpenVPN、分流用 mihomo 都在虚拟机里跑。测试用的对端也起在同一个虚拟机的另一个命名空间里，不依赖任何外部账号（决定 1）。经 vm-up 的新阶段跑，不接管宿主网络。
- **镜像构建**：下载 Alpine 的 .apk 到 `guest/out/`（允许的操作）。
- **查出口位置的第三方服务**：会话里每个查询源各查一次，用来采样本；请求不带项目或用户信息；样本里的地址和位置换成文档用的值再入库（决定 4）。
- **只读查询**：`systemsetup -gettimezone` 这类读命令如果需要 root，就不执行，改用录制的样本；`defaults read -g AppleLanguages` 等不需要 root 的读命令可以执行，用来采样本。

### 0.2 会话里绝不执行（决定 2、3）

- 沿用 m2-plan 0.1 的清单：sudo、pfctl（`-n` 除外）、networksetup -set*、ifconfig、route 写操作、scutil 写操作、创建 utun。
- **结束 Claude 进程的真实实现**：开发会话自己就是 Claude Code。真实实现第一步检查有效 uid 为 0，不是就拒绝；源码检查保证只有真实模式的入口能调用它；测试只用假进程表和假的信号发送器。
- **改 Mac 的时区、自动时区、语言**：`systemsetup -settimezone`、写 `com.apple.timezone.auto`、`defaults write -g AppleLanguages/AppleLocale`、改 `/Library/Preferences/.GlobalPreferences`。只做参数拼装和输出解析，用命令模拟器测；真机由 M4-9 的用户脚本验证（R4）。

### 0.3 需要用户的部分

全部归到 M4-9 的真机脚本：R4（时区和语言在真机上的效果）、R5（真实服务商的 .ovpn、.conf）、地区切换与还原、带人为泄漏的环境检测、真实模式下的强制结束 Claude、R7、R16。M3 遗留的清单第 6、7 步不变。

### 0.4 M4 开工的 7 条决定（已回写 design v0.7）

1. 先验证有风险的前提（R19、R5），排在最前（M4-1）；对端起在同一个虚拟机里。
2. 结束 Claude 进程的真实实现，会话里永远不执行（10.1）。
3. 改 Mac 的时区、自动时区、语言的命令，会话里不执行（9.2、R4）。
4. 查出口位置的第三方服务：录制样本加进程内假服务测试；会话里各查一次采样本，请求和样本脱敏（16）。
5. 闸门带关闭原因，所有原因消除才打开；M2 的最小出口检查和 M3 的“出口 30 秒不可用”由正式检查替换（8）。
6. “无法判断”不等于不通过：换源重试、沿用上一次结论，最多 10 分钟；同国漂移不关闸门（8）。
7. 本机真实公网 IP 经直连拨号模块测，结果只在内存里（8.1）。

## 2. 各任务

### M4-1 探查 R19、R5（镜像、命名空间、同机对端）

**镜像（R19）**：

- `internal/imagebuild/apk.go`（新）：
  ```go
  type APKPkg struct{ Name, Version, Arch string; Depends, Provides []string; Size int64 }
  func ParseAPKINDEX(r io.Reader) ([]APKPkg, error)              // 解 APKINDEX.tar.gz 里的 APKINDEX 文本
  func ResolveAPK(index []APKPkg, want []string) ([]APKPkg, error) // 按 D:/p: 做依赖闭包（含 so: 和 cmd: 提供项），去掉 minirootfs 已有的
  func ExtractAPK(r io.Reader, t *Tree) (APKMeta, error)          // .apk 是三段 gzip tar：签名、控制、数据；只把数据段放进根树
  type APKMeta struct{ Name, Version string; Scripts []string }   // 记下有哪些安装脚本（不运行）
  ```
- `guest/manifest.json` 加 `packages`：每个包一条 `{name, version, url, sha256}`，由 `abroad-imagebuild pin-packages <名字…>` 生成（读 APKINDEX、解依赖、下载、算哈希、写回清单）。正式构建只按清单下载并校验哈希，**不在构建时解依赖**，这样构建可复现。
- 要装的包：`openvpn`、`wireguard-tools`（`wg`、`wg-quick` 及其依赖）、`nftables`、`iproute2`、`tzdata`、`musl-locales`（M4-5 用；装不上记进实测项）。内核模块 `wireguard`、`nf_tables`、`nft_*`、`veth`、`tun` 从 netboot 的 modloop 取，沿用 `internal/kmod` 的加载方式。
- 安装脚本不运行：逐个看清单里包的 `.pre-install`、`.post-install`，必要的动作（建用户、建目录）由 imagebuild 等价完成，写进 design 7.1。

**命名空间与同机对端（R5）**：agent 的开发接口 `POST /v1/dev/netns-probe`（只在 `abroad.dev=1` 时注册，沿用 dev-exits 的门槛），在虚拟机里：

1. 建出口命名空间 `x1` 和对端命名空间 `peer`，用 veth 连起来（对端地址模拟“VPN 服务器”）；
2. `peer` 里起 WireGuard 服务端、OpenVPN 服务端（静态密钥或自签证书，配置在探查代码里生成，不依赖外部账号）；
3. `x1` 里 `wg-quick up`、`openvpn --config <改写后的配置>`（R5 的改写：去掉 `redirect-gateway` 之外的影响宿主的指令，加 `route-nopull` 的等价），确认隧道接口成为 `x1` 的默认路由；
4. `x1` 里加 nft 断网规则（只放行到对端端点的 UDP/TCP 和 veth 对端），断开隧道后确认 `x1` 只能连对端；
5. 回报 JSON：每一步的结果、耗时、出错时的命令输出（不含密钥）。

**验收**：

- a. 镜像构建可复现：同一份清单连续两次构建，根镜像的 SHA-256 相同；`verify` 校验每个 .apk 的哈希。
- b. 解析、解依赖、解包的单测：APKINDEX 样本（录制，入 testdata）、循环依赖、缺包、`so:` 提供项、三段 gzip 的 .apk 样本。
- c. vm-up 新阶段（10a）调用 `netns-probe`：WireGuard、OpenVPN 各通一条隧道（经隧道 ping 对端隧道地址、TCP 回显）；断开后 `x1` 只能连对端；报告全部 ok。
- d. 结论写进 design 15 的 R19、R5；不行时给出备选（R19：容器构建；R5：不改写配置、只靠命名空间隔离）的评估。
- 本机环境仍拒绝绑物理网卡时，c 只能做到“镜像构建、单测”，虚拟机部分记为被本机环境挡住（vm-up 的出站要绑物理网卡；但 netns-probe 本身不出虚拟机，若虚拟机能起来就能跑，见“需要实测”一节）。

**【v2】M4-1 的补充**（architect 审 v1）：

- **来源校验**（建议改 9）：`pin-packages` 除了走 HTTPS，还用 Alpine 的公钥校验 `APKINDEX.tar.gz` 的签名（索引里第一段 gzip 是 `.SIGN.RSA*.pub` 签名，公钥随仓库保存在 `guest/keys/`）；再按索引里的校验和核对每个 .apk 的控制段。做不到时在 design 7.1 写明“清单的改动需要人工复核”，并让 `pin-packages` 输出新旧清单的差异。
- **解包的路径安全**：拒绝带 `..`、绝对路径、指向根外的符号链接；安装脚本只记录、不执行。
- **WireGuard 用不用 `wg-quick`**（建议改 8）：探查时评估由 agent 自己建接口、配地址和路由，只调 `wg setconf`（`wg-quick` 是 shell 脚本，依赖 bash 和别的工具）。结论写进 R5。
- **验收按 architect 给的 a–h**（PROGRESS 当前任务）：列出 v1 到 v2 改动的段落；解析、闭包、解包的单测（含版本约束、拒绝的路径）；可复现和哈希改错一位时构建失败并指出包；签名校验的测试；虚拟机里的探查（隧道断开后 53 端口也不通，报告里没有密钥），起不来时如实记为被本机环境挡住；结论写进 R19、R5；探查接口只在开发构建和开发标记下存在；全量构建和测试。

### M4-2 出口检查 `internal/exitcheck`

复用 `internal/exitpolicy`（改掉 Cage 字样的文案和 UA；加 Cloudflare trace 源；把 static/dynamic + Scope 映射到 design 8 的四条规则）。

```go
type Result int // Pass, Fail, Unknown

type Geo struct{ IP netip.Addr; Country, Region, City, Timezone, ASN, Org string }

// GeoSource 是一个查询源（ipwho.is、IP.SB、Cloudflare trace），经给定的 HTTP 客户端（走指定出口）查询。
type GeoSource interface {
	Name() string
	Lookup(ctx context.Context, hc *http.Client) (Geo, error) // 超时、限流（429）、格式不对 → 错误（调用方按 Unknown 处理）
}

type Baseline struct{ Geo Geo; Rule Rule; At time.Time } // 应用主代理时保存（state 目录，0600）
type Rule int // FixedIP, SameCity, SameCountry（默认）, Any

type Item struct{ Name string; Result Result; Detail string } // detail 不含地址
type Report struct {
	Exit    string
	Items   []Item  // https、udp、ip、geo、doh
	Geo     Geo     // 只在内存和 status 的脱敏摘要里
	Verdict Result
	At      time.Time
}

type Checker struct {
	Opener  stack.Opener    // 经指定出口开流（不经闸门）
	Sources []GeoSource
	HTTPSURL string          // 默认 https://www.gstatic.com/generate_204，以收到 204 为准
	UDPProbe netip.AddrPort  // 默认 1.1.1.1:53，以收到 DNS 应答为准
	DoHName  string
	Now     func() time.Time
}
func (c *Checker) Check(ctx context.Context, exit string, base *Baseline) Report
func Compare(base Baseline, now Geo) (Result, string) // 出口变化规则；大陆段一律 Fail
```

- HTTPS 探测在数据流上做真正的 TLS 握手和 HTTP 请求，以收到预期应答为准（M1-4e 的待办）；UDP 探测以收到应答为准（M1-6c-2 的备注）。
- 查询源依次换：ipwho.is → IP.SB → Cloudflare trace；全部失败是 `Unknown`；任何一个明确测到大陆段或违反规则是 `Fail`。
- 主代理的 UDP 不通过：记录，不影响放行（design 8）；分流出口的 UDP 不通过：该出口的 UDP 改走主代理（M4-8 接）。

**验收**：

- a. 四种变化规则的表驱动测试，含同国换城市（SameCountry 下通过）、换国家（不通过）、大陆段（任何规则下不通过）、基准为空（应用主代理时）。
- b. 查询源的解析器用录制样本测（每个源成功、429、超时、HTML 错误页、字段缺失各一例）；样本的地址和位置是文档用的值。
- c. 进程内假查询源：第一个超时、第二个成功 → 用第二个；全部失败 → Unknown；一个说大陆 → Fail。
- d. HTTPS 探测：CONNECT 成功但对端不回 HTTP、回 200 而不是 204、TLS 证书不对，都不是 Pass。
- e. UDP 探测：数据面回 ok 但没有应答 → 不是 Pass（M1-6c-2 的场景，用 mihomo `MATCH,REJECT` 的等价假出口）。
- f. 性质测试：Unknown 永远不会由单次网络错误变成 Fail。
- g. 会话里各查一次真实查询源采样本（不带项目信息的 UA，例如 `Mozilla/5.0`），脱敏后入 testdata。

**【v2.1】M4-2 的补充决定**（architect 2026-11-19 判 M4-1 时给出）：

1. **“出口 IP 是多少”和“这个 IP 在哪里”分开查，位置结果按 IP 缓存**（回写 design 8）：每次复查只做 HTTPS 探测和取出口 IP（轻量的源，例如 Cloudflare trace，同时给国家代码；多个源轮换）；是否在大陆段用内嵌地址段本地判断，每次都做；城市、州省、时区、运营商只在出口 IP 与缓存不同时查，按 IP 缓存 24 小时（内存和基准文件里）。规则是“同一国家”“不限”时只用国家代码和本地大陆段，不做位置查询；“同一城市”时 IP 变了才查一次。
2. **各项探测有独立时限**，一轮总时限不超过 20 秒；超时一律“无法判断”。
3. **判定表在代码里只定义一次**：不通过 = 明确在大陆段、明确违反出口变化规则、HTTPS 收到了应答但不是预期的（被劫持、证书不对）；无法判断 = 超时、连接失败、查询源限流或格式异常、数据通道不可用。连接失败持续 10 分钟才按不通过处理（M4-3）。**例外**：启用时的那一次检查，“无法判断”不能放行（写进 M4-3）。
4. **敏感字段**：出口 IP 只在内存里的报告和基准文件（0600）；日志一律脱敏；status 只给国家、时区和各项结果，不给 IP、城市、运营商（完整信息经需要授权的接口给界面，M5）。
5. **会话里的真实采样**：每个查询源各查一次；请求头用通用的浏览器标识；地址、位置、运营商全部换成文档用的值再入库；原始应答不落盘到仓库目录。
6. **基准文件**：状态目录，属主才能读写，原子写；读不出来或校验不过时当作“没有基准”，启用要求重新“应用主代理”，不能跳过比对。

**验收（M4-2）**：architect 给的 a–k（PROGRESS 当前任务），替换本节原来的 a–g。

 `internal/gatesm`

复用 Cage `internal/gate` 的状态机思路（epoch、租约、报告校验），不搬它的出站和 Cage 检查项（见第 5 节）。替换 `internal/daemon/gate.go` 的原子开关，保留只读视图 `GateView`、`hook`、断开顺序（`Proxy.DropAll` → DoH `Close` → 拨号器 `Close`）。

```go
type Reason string // takeover、exit_check、env_check、state
type State int     // Closed, Checking, Open

type Gate struct{ /* 时钟可注入 */ }
func (g *Gate) Close(r Reason, detail string)          // 加一个原因（立即关闭）
func (g *Gate) Clear(r Reason)                         // 只清自己的原因
func (g *Gate) BeginCheck() uint64                     // 进入 Checking，返回 epoch
func (g *Gate) Grant(epoch uint64, lease time.Duration) bool // 检查通过：epoch 没过期才放行，lease 默认 90 秒
func (g *Gate) Open() bool                             // 没有原因、且租约没过期
func (g *Gate) Status() Status                         // State、Reasons、LeaseUntil（status 用）

// ExitAvail 是按出口的可用状态（替换 M3 的 exitDown）：主代理 Fail → 闸门 Close(exit_check)；
```

**【v2.2】M4-3 的补充决定**（architect 2026-11-19 判 M4-2 时给出；同时是 M4-3 的实施计划）：

1. **“放行期到期”不是需要别人清的原因**：闸门打开 = 没有任何关闭原因且放行期有效。到期时走关闭路径（断开走代理的连接），记一条 `lease_expired` 事件；下一次放行自然恢复。关闭原因只有四种：`takeover`（本机接管故障）、`exit_check`、`env_check`、`state`（状态不是启用）。各方只能清自己加的。
2. **复查循环只在状态是启用时运行**：停用、恢复、未启用时不发任何探测。每 60 秒一轮；监护清掉 `takeover` 时、状态切到启用时，立即补一轮。
3. **三种结果**：通过 → 清 `exit_check`、放行 90 秒；不通过 → 加 `exit_check`；无法判断 → 最近一次明确通过在 10 分钟内就续期，否则加 `exit_check`。“最近一次通过”只在内存里，进程重启后必须重新明确通过一次。
4. **启用流程**：第 ⑤ 步的出口检查必须明确通过，无法判断按失败处理并回滚。第 ⑧ 步：写入 ENABLED、通知数据面、清 `state`；第 ⑤ 步的通过结果不超过 30 秒时直接用它放行，超过就立即补一轮复查，没通过也不回滚（状态 ENABLED、闸门关着，由复查循环接手）。Recover 在 ENABLED 下不再自己做检查和开闸门，只重建并清 `state`，其余交给复查循环。
5. **监护的职责收窄**：只管 `takeover`：核对不通过就加，修复并复核通过就清。原来“启动虚拟机、做出口检查、退避后重开闸门”那一段删掉，由复查循环替代；M2-7e 的用例改写成等价断言：故障消除后，在下一轮复查通过时重新打开。
6. **没有基准不能启用**：加一个属主才能调用的接口“建立基准”：经主代理跑一轮带位置查询的检查，按给定规则保存（默认同一国家）。启用时没有基准或读不出来：拒绝启用，提示先建立基准。M4-5 再并进“应用主代理”的两步确认。
7. **按出口的可用状态**：接口按多出口做，替换 M3 的“30 秒不可用”标记。M4-8 接上正式的分流出口之前，开发用的多出口没有检查结果，按“可用，除非最近一次开流明确回了出口不存在或不可用”处理（保留 M3 那条判断作为输入之一），M4-8 再收口。
8. **闸门对外的只读视图保留**（网络栈和 fake-IP DNS 用的），另加“当前是否只剩 `env_check` 这一个原因”的查询，给 M4-6 的探测放行用；M4-3 里不做放行本身。

**验收（M4-3）**：architect 给的 a–l（PROGRESS 当前任务）。另删除不再被引用的 Cage 包 gate、netguard、diagnostics、hostproxy（NOTICE 和许可证文件保留）。

**【v2】M4-5 的补充**（architect 审 v1）：

- **必须改 2：启用和切换地区不能悄悄结束 Claude**。启用、应用主代理、切换地区这三个会导致地区变化的操作，都走和恢复相同的两步：先预览，返回“地区从 A 变为 B”、将被结束的进程清单和确认码；带确认码的第二次请求才执行。地区不变时不需要确认码。不带确认码又需要结束进程时，接口回“需要确认”（HTTP 409，带预览内容），不做任何改动。测试：地区会变且不带确认码 → 没有任何进程被结束、系统没有改动（状态文件、命令记录都不变）；确认码过期或错误 → 同上；地区不变 → 直接执行。回写 design 9.3、11.1。

**【v2.4】M4-5 的补充决定**（architect 2026-11-20 判 M4-4 时给出；M4-5 一节和 v2 的三条补充照做，再明确以下几点）：

1. **“地区会不会变”**：目标地区（时区、首选语言、地区格式）与此刻从 Mac 上读到的值逐项比较，任何一项不同就算会变；会变时才需要结束 Claude 和两步确认。读不出当前值时不做任何修改，操作失败并说明原因（没有原值就没法保证回国时还原）。
2. **写入顺序固定，每一步之前先落盘**：记原值（只在从 RESTORED 启用时）→ 记目标 → 结束 Claude → 虚拟机内的时区和语言 → Mac 时区 → 关自动时区 → 当前登录用户的语言和地区格式 → 系统级的语言设置。还原按相反的顺序，每一步可重入。崩溃穷举覆盖每一步。
3. **虚拟机里改完地区后引擎会重启**：启用流程在地区同步之后等虚拟机恢复，并重新明确通过一次出口检查，再往下走；“第 ⑤ 步的通过时间”以这一次为准。
4. **“应用主代理”成形**，把 M4-3 的“建立基准”并进来：跑一轮带位置查询的出口检查 → 保存基准 → 按基准算出目标地区 → 已在启用状态时再执行地区同步；未启用时只保存基准和目标，等启用时再同步。主代理配置下发给虚拟机仍由现有的开发工具在此之前完成。原来的建立基准接口保留为别名或删掉，二选一并写明。
5. **“切换地区”**：手动指定时区和语言，或回到“跟随出口”；只改地区，不影响网络状态；改完后如果状态是启用，立即补一轮复查（环境检测的补跑等 M4-6）。
6. **出口复查不改地区**：复查发现出口的时区或国家与锁定的目标不同时只产生事件；国家不同由 M4-6 的环境检测第 03 项处理，M4-5 里不因此关闸门、不改任何设置。
7. **改 Mac 设置的命令经带路径白名单的执行器**（沿用 sysnet）：白名单增加 `systemsetup`、`defaults`、`launchctl`、`sudo`。本任务只做参数拼装和输出解析。参数进命令行之前校验：时区必须是内置时区数据库里存在的名字；语言和地区格式必须符合语言标签的写法；用户名和 uid 来自 `/dev/console` 的属主，不接受外部传入。命令模拟器扩展出时区、自动时区、语言的假状态；commands.golden 的新增形态逐条审过再更新。
8. **不需要 root 的读命令可以在会话里执行一次采样**（例如读当前用户的语言列表），样本如实保留；需要 root 的读命令不执行，用构造样本并标明，真机格式由 M4-9 核对。

**验收（M4-5，v2.4）**：

- a. 目标的计算：国家到语言的映射表驱动测试；查询源给的时区不在内置数据库里时拒绝；手动指定的时区、语言不合法时拒绝；“跟随出口”和“手动”两种来源都能锁定；锁定之后只有启用（首次）、应用主代理、切换地区三个操作能改变目标（调用记录断言）。
- b. 命令拼装与解析：逐字核对每条命令的路径、参数；带空格的时区名、多语言列表（目标放第一位，原有的其余语言按原顺序保留，不重复）；原来没有键时还原用删除；没有人登录时跳过用户级的语言并发事件；非法输入在调用执行器之前报错。解析样本：会话里采到的读命令输出，加标明为构造的样本。
- c. 状态机：崩溃穷举和重启穷举加入地区的每一步后全部通过，注入点数增加；任何一步中断后重启，原值不丢、不被已经改过的值覆盖；恢复后时区、自动时区、语言、地区格式逐项等于假系统的初始值；从 DISABLED 再启用时不重拍原值；用户在回国期间自己改过设置时，下一次从 RESTORED 启用以新的为准。
- d. 读不出当前值：启用失败，系统没有任何改动，状态文件未写入地区字段，没有结束任何进程。
- e. 两步确认：启用、应用主代理、切换地区在地区会变时，不带确认码回 409，带“从 A 变为 B”和进程预览，系统没有改动、没有信号；带正确的确认码时执行，Claude 进程先被结束，再改设置；结束不了时中止，地区和网络都不变；地区不变时不需要确认码，也不结束任何进程。

- g. 出口漂移不改地区：复查得到同国不同时区、或不同国家的结果时，Mac 的命令记录没有新增，目标不变，有事件；闸门不因此关闭。
- h. 虚拟机一侧：agent 的接口只写三个文件（假文件系统断言没有碰别的路径）；时区名、语言不合法时拒绝；写入后引擎被重启一次；重复下发同样的值时不重启。
- i. 命令审计：commands.golden 的新增形态只有本任务列出的那些（交验收时列出新增的行）；新增程序的路径都是绝对路径；测试里真实的执行器不可达，源码检查沿用现有做法。
- j. 日志和 status：地区的目标和来源可以显示；原值不进日志；确认码不进日志。
- k. M2、M3、M4-1 到 M4-4 的全部用例仍通过；go build、go vet、GOOS=linux GOARCH=arm64 go build、带开发标签的构建、`go test -race -count=1 ./internal/... ./cmd/...` 全过。会话里不用 sudo，不执行任何改时区、改语言的命令，不改宿主机网络，不向任何进程发信号。

### M4-6 环境检测 `internal/envcheck`

全部按 design 8.1 的描述自己实现，不复制 claude-switcher（AGPL）的任何代码、脚本或文案。

```go
type Level int   // Hard, Warn
type Outcome struct{ Result exitcheck.Result; Detail string /* 不含地址 */ ; Fix string }
type Item interface{ ID() string; Level() Level; Run(ctx context.Context, e *Env) Outcome }
type Env struct { // 每一项要用到的依赖，测试里全部注入
	Takeover  TakeoverView         // 01：pf 摘要、utun 路由、DNS、后台服务
	Exit      *exitcheck.Checker   // 02、03
	Region    region.Target        // 03、04、05
	Mac       region.Mac           // 04、05（读）
	Dial      func(ctx context.Context, network, addr string) (net.Conn, error) // 本机发起的探测，经 utun（06、07、10）
	Direct    DirectUDP            // 08：经直连拨号模块拿 UDP 连接（决定 7）
	Procs     claudeproc.Table     // 12、17

func (r *Runner) RunAll(ctx context.Context) Report
```

- **探测流量的放行**（启用第 ⑦ 步闸门还关着时）：网络栈对“应用是 abroadd 自己”（procinfo 查到的进程号等于 abroadd 的进程号）的连接放行，其余仍按闸门。
- **第 08 项**：`Direct.Dial(ctx, "udp", "stun.l.google.com", 19302)` 拿到 UDP 连接，自己发 STUN Binding；结果只在内存，只输出比较结论（决定 7）。全球、国内各两个 STUN 服务器经 utun 发。
- **第 12、17 项**：`procinfo` 加读进程环境变量（`kern.procargs2` 里参数之后就是环境变量），只取 `HTTP(S)_PROXY`、`ALL_PROXY`、`LANG`、`LC_ALL`。
- **调度**：启用时、每 10 分钟、网络切换、更换主代理、切换地区、改 Claude 的分流规则后立即；Claude 启动前（M6）结果超过 10 分钟就补跑。
- **与闸门联动**：硬性项明确不通过 → `Close(env_check)`；全部通过（或 Unknown 在 10 分钟内）→ `Clear(env_check)`；依赖外部服务的项按 5、15、45 秒重试三次。
- **设备体检**（字体扫描）放到 M5（只是应用里的手动功能，不参与放行）。

**验收**：

- a. 每项三种结果都有用例（17 × 3，警告项的“不通过”即警告）。
- b. 人为制造泄漏能检出（进程内注入）：DNS 不指向 198.18.0.2、STUN 回报真实 IP 或大陆地址、IPv6 能连通、系统代理打开、Claude 进程带 `HTTPS_PROXY`。
- c. 查询服务不可用 → Unknown，不关闸门；Unknown 超过 10 分钟 → 按不通过关闸门。
- d. 警告项不阻断、可关闭（关闭后显示“已跳过”）；硬性项不能关闭。
- e. 日志脱敏：结果写日志时出口 IP、真实 IP、STUN 回报地址都不出现（日志泄漏测试，同 M3）。
- f. 第 08 项：真实 IP 不落盘、不进 status（检查 status JSON 和状态目录的所有文件）。

**【v2.6】M4-6 拆成两步**（architect 2026-11-20 判 M4-5 时给出）：

- **6a**：框架、调度、与闸门的联动、启用第 ⑦ 步、探测流量在闸门关着时的放行（探测窗口）；检查项 01、06、07、09、11（只看本机状态，或只用我们自己的 DNS）。
- **6b**：依赖外部服务或要读写系统设置的项 02、03、08、10、04、05、12–17；出口历史；本机真实 IP 的测量；R10。
- 拆开的原因：6a 的“闸门关着时放行自己的探测”要在网络栈里开一条特殊路径，是 M4-6 里唯一碰“不泄漏”主干的地方，单独审。

**【v2.6】M4-6a 的设计决定**：

1. **先后依赖**：01（接管就绪）不通过或无法判断时，同一轮里所有要发网络探测的项都不执行，结果记“无法判断：接管未就绪”。01 复用监护的核对：pf 保护有效、utun 活着、路由经我们的 utun 且没有冲突、DNS 在。
2. **探测窗口**（替代 M4-3 的“只剩 env_check 一个原因”）：闸门加打开、关闭探测窗口的方法；没有 takeover、exit_check 两个原因时才能打开，任一出现立即失效；默认时限 90 秒，到时自动关闭，调用方用完也主动关。窗口期间网络栈对“识别为 abroadd 自己进程”的连接放行，固定走主代理：不经规则引擎、不可能直连、不受数据面“停用”影响；其他连接照常。放行的连接单独计数。这是网络栈里唯一一条不经规则引擎的转发路径，源码检查把它列为唯一例外、断言它只能产生“走主代理”。窗口期间强制识别应用；识别不到或不是自己就不放行。
3. **启用第 ⑦ 步**：地区同步和再次出口检查之后、写 ENABLED 之前：打开探测窗口 → 跑全部硬性项 → 关闭窗口。硬性项全部明确通过才继续；不通过，或按 5、15、45 秒（时钟注入）重试后仍无法判断，启用失败并回滚，错误里列出是哪几项和怎么修。警告项不影响启用。
4. **运行中**：每 10 分钟一轮；规则里 Claude 的去向变化、切换地区、应用主代理、监护清掉接管故障之后立即补一轮（网络切换的触发留给 6b）。硬性项明确不通过 → 加 env_check 原因（闸门关、已有走代理的连接断开）；全部通过 → 清原因并触发一次出口复查来重新放行；无法判断 → 沿用上一次结论最多 10 分钟（只在内存里，重启后必须重新明确通过）。因环境检测关了闸门后，下一轮检测用探测窗口发探测。不结束正在运行的 Claude。
5. **警告项可以由用户关闭，硬性项不能**。关闭的项显示“已跳过”，不算通过、不参与判定。设置存在状态目录的文件里（0600），修改接口属主才能调用。
6. **6a 的五项**：01 接管就绪（决定 1）；06 IPv6（各网络服务的 IPv6 都已关闭，复用 sysnet 的快照，M2-8 的 unknown 单独列出、不算不通过；尝试连接一个只有 IPv6 的地址必须失败，连接函数可注入）；07 DNS（经系统解析器解析测试域名，结果必须在 fake 段内；回显解析器那一半放 6b）；09 Claude 去向（只调用规则引擎：Claude 桌面版、Claude Code 访问 claude.ai 必须走代理且出口可用；本机网络的普通应用访问 claude.ai 必须走主代理）；11 系统代理与其他接管（复用冲突检查的系统代理、PAC、自动发现、路由冲突，带上我们自己的 utun 名）。
7. **结果的三种取值沿用 exitcheck 的类型**；每项输出结果、不含地址的说明、修复办法；整轮结果进 status 和事件，日志脱敏。
8. **Claude 的域名字面量只允许出现在规则引擎的置顶名单和第 09、10 项里**（源码检查）。

**验收（M4-6a，v2.6）**：

- a. 五个检查项各有通过、不通过、无法判断三种用例（注入依赖）；06 里没动过的 unknown 服务不算不通过；09 的三种判定各有不通过的例子（Claude 的出口不可用；绕过校验把 Claude 设成直连；普通直连应用访问置顶域名没被改走主代理）。
- b. 先后依赖：01 不通过或无法判断时，要发网络探测的项的执行函数调用数为 0，结果是无法判断并注明原因；只看本机状态的项照常执行。
- c. 探测窗口（gatesm，时钟注入）：有 takeover 或 exit_check 时打不开；打开后两者任一出现立即失效；到时限自动关闭；重复开关安全；窗口不改变闸门的开关（IsOpen 仍是关）。
- d. 网络栈的放行（进程内全链路，假识别器按源端口给进程号）：窗口打开、来自自己的连接经主代理到达（即使数据面停用、闸门关、规则是直连或拦截）；别的进程照常被拒；窗口关闭后自己的也被拒；识别不到不放行；放行的连接直连调用数为 0；单独计数；规则不需要识别时窗口期间仍识别。
- e. 源码检查：网络栈里“开代理流”的调用点只多出这一处且出口是主代理常量；“直连拨号”的调用点没有增加；Claude 的域名字面量只出现在允许的文件里。
- f. 启用第 ⑦ 步：全部通过 → 成功，窗口已关；某硬性项不通过 → 失败并回滚干净（地区也还原），错误里有修复办法，闸门从未打开；无法判断按 5、15、45 秒重试，其间通过则成功，始终无法判断则失败并回滚；警告项不通过不影响；崩溃穷举加入第 ⑦ 步后仍通过。
- g. 运行中：每 10 分钟一轮；硬性项不通过 → 闸门关（原因 env_check），已有走代理长连接 1 秒内被断、直连保持；修复后下一轮通过、原因清除、出口复查重新放行；闸门因环境检测关着时，下一轮的探测经探测窗口发出（需要发探测的假项目）；无法判断 9 分 59 秒不关、10 分 1 秒关；重启后必须重新明确通过；四个触发补跑的时机各有用例。
- h. 警告项的开关：关闭后显示“已跳过”、不参与判定；硬性项关不掉（接口报错）；设置文件 0600，重启后保留；接口沿用对端身份校验。
- i. status 里有每项的结果、说明和修复办法；日志泄漏测试搜不到测试用的地址和域名。
- j. M2、M3、M4-1 到 M4-5 的全部用例仍通过；没有配置环境检测时（假系统的最小模式）行为与现在相同；全量构建和 -race 测试完整跑一遍。

**【v2.7】M4-6b 的设计决定**（architect 2026-11-20 判 M4-6a 时给出）：

1. **本机发起的探测只有一个出口函数**（envcheck 的一个文件，“不准直接拨号”检查的唯一白名单）：用系统默认的方式拨号，不绑网卡、不走代理，经 utun 进我们的网络栈；只在同一轮 01 通过之后才被调用。
2. **02 出口 IP、03 出口地区**：经探测出口访问取 IP 的源，复用 exitcheck 的解析器、大陆段判断和位置缓存。02 按基准和出口变化规则比对；03 要求不在大陆段、国家等于锁定目标的国家；地区同步没接时只判大陆段。
3. **04 时区、05 语言**：读 Mac 当前值与锁定的目标比较，自动时区必须是关的；不一致时先经状态机的新操作自动改回（只写不同的项、不结束 Claude、拿操作锁），改完重读，仍不一致才算不通过；同一项连续 3 轮都要靠改回时提示“可能有别的软件在改”；地区同步没接时这两项“已跳过”。
4. **07 后一半**：经我们的 DNS 查一条回显解析器地址的记录，对回显地址做大陆段判断；查询失败是无法判断。
5. **08 STUN**：经探测出口向四个 STUN 服务器（全球两个、国内两个，可配置）发 Binding 请求。不通过：任一回报地址等于本机真实公网 IP，或在大陆段，或国家与出口不同（国家用位置缓存，查不到时该条件无法判断）。主代理已知不支持 UDP 时全部无响应算通过；支持 UDP 却全部无响应是无法判断。本机真实公网 IP：启用时和网络变化时经直连拨号模块按域名取 UDP 连接、向一个 STUN 服务器测一次，只在内存里；测不到时“等于真实 IP”这一条无法判断。
6. **10 Claude 可达性**：不经 utun，经数据通道按“规则里 Claude 实际走的出口”开流（同 exitcheck），每个不同的出口各测一次；目标 claude.ai、api.anthropic.com；完成 TLS 握手（证书照常校验）并收到任意 HTTP 状态码即通过；握手失败或证书不对是不通过；超时、连接失败是无法判断；通用浏览器标识、最简单的请求、不带凭据。会话里的测试只用假的对端。
7. **12 Claude 进程环境、17 终端语言**：procinfo 读进程环境变量，只取 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY（含小写）和 LANG、LC_ALL；12 只报“有没有”和变量名，不读出值；对象是 claudeproc 扫描到的 Claude 根进程；“即将启动的进程”属于 M6。
8. **13 IP 稳定性**：保留 48 小时的出口变化记录；落盘的是用本机随机密钥算出的摘要，不是 IP；文件 0600。
9. **14 网络类型**：用位置查询返回的运营商和组织名，按内置关键词表判断是否疑似机房；只是警告；没有这些字段时无法判断。
10. **15 Claude 客户端语言（R10）**：先在会话里只读地找桌面版保存界面语言的位置；找得到就实现，找不到时固定“已跳过：未能确定配置位置”，结论写进 design R10，列入 M4-9。
11. **16 浏览器语言**：只读当前登录用户的 Chrome、Edge 默认配置里的首选语言，文件大小有上限，解析失败是无法判断；Safari 跟随系统，不查。
12. **网络变化的触发**：监护每轮的网络快照里直连网段或默认出口变了，就触发一次环境检测并重测本机真实公网 IP。

**验收（M4-6b，v2.7）**：全部用注入的依赖和进程内的假服务（k 除外）。

- c. 人为制造泄漏能检出（各一例）：取 IP 的源回报的地址不符合基准规则；出口国家与目标不同；出口在大陆段；解析器的回显地址在大陆段；STUN 回报本机真实 IP；STUN 回报大陆地址；STUN 回报的国家与出口不同；Claude 进程带代理环境变量（大小写各一例）；时区被改回且改不回来；自动时区被重新打开。

### M4-7 虚拟机内分流出口引擎

```go
// internal/agent：
type ExitSpec struct {
	Tag  string
	Kind string // wireguard、openvpn、clash（订阅 mihomo）
	Conf []byte // 凭据和配置，只经 ctl.sock 下发到 tmpfs /run/claude-abroad/exits/<tag>/，不进日志
}
// PUT /v1/exits：替换全部分流出口（幂等）；dev-exits 继续只在 abroad.dev=1 时存在。
type NSManager interface {
	Up(ctx context.Context, tag string, n int) (Netns, error) // ip netns add、veth（10.200.<n>.1/30 ↔ .2/30）、root ns 的 NAT
	Down(ctx context.Context, tag string) error
}
// 每个 VPN 出口：命名空间里 nft 断网规则（只放行到 VPN 端点和 veth 对端）→ 起 VPN → 在命名空间里运行
// `abroad-agent socks --listen 10.200.<n>.2:1080`；sing-box 加 socks 出站指过去。
// clash：每个订阅一个 mihomo 进程，监听虚拟机回环的 mixed 端口；配置用分流专用的白名单校验（mihomocfg 另一套）。
```

- `ExitTable` 扩展：出口可用 = 引擎在运行且（VPN 类）隧道接口在。
- OpenVPN 配置改写（R5 的结论决定具体做法）；WireGuard 用 `wg-quick up <conf>`（`Table`、`PostUp` 等危险指令按白名单处理）。
- 凭据：`/run/claude-abroad` 是 tmpfs；下发的请求体、配置内容不进日志（日志泄漏测试）。

**验收**：

- a. 对同机对端的端到端（vm-up 阶段 10b）：经 data.sock 指定出口 WireGuard、OpenVPN、clash（开发上游当订阅节点）各连一次 TCP 回显，回显来自对应的对端。
- b. 隧道断开时该出口不泄漏：命名空间里只有到对端端点的包（在 `peer` 侧计数）；数据面对该出口开流失败（`exit_down`），不改走直连。
- c. 凭据只在 tmpfs、不进日志：日志和 `/data` 里搜不到测试密钥。
- d. 多个引擎同时运行：三个出口并发各 50 条流，全部到达对应对端。
- e. R20 的断言：每种出口类型都确认没有隐式直连（netstats 里绑物理网卡的拨号不增长）。

**【v2】M4-7 的补充**（architect 审 v1）：

- **必须改 3：走分流出口的连接，域名解析在那条隧道里做**。命名空间里的 `abroad-agent socks` 解析域名只经隧道：用配置里给的 DNS（WireGuard 的 `DNS=`、OpenVPN 推送的 `dhcp-option DNS`）；没有时用一个固定的公共解析器（1.1.1.1），经隧道访问。不退回虚拟机根命名空间的解析路径，解析失败就是失败。命名空间的断网规则把 53 端口也算进去：隧道断开时解析一并失败。订阅 mihomo 的出口由它自己解析，分流用的配置白名单要求它的 DNS 也经节点（`dns.respect-rules`、`proxy-server-nameserver` 之类按 mihomo 的实际字段定）。测试：对端一侧统计 53 端口的查询，正常时查询出现在隧道里；断开隧道后根命名空间和 veth 上都看不到该出口发出的查询；该出口的连接回 `exit_down`。
- **建议改 8：VPN 配置按指令白名单处理**：
  - WireGuard 只认 `[Interface]` 的 `PrivateKey`、`Address`、`DNS`、`MTU`，`[Peer]` 的 `PublicKey`、`PresharedKey`、`Endpoint`、`AllowedIPs`、`PersistentKeepalive`；`PreUp`、`PostUp`、`PreDown`、`PostDown`、`SaveConfig`、`Table` 等一律拒绝并指出是哪一行。
  - OpenVPN 列允许的指令清单；脚本类（`up`、`down`、`route-up`、`script-security`、`plugin`、`management` 等）和引用外部文件的指令一律拒绝，证书密钥只收内联形式（`<ca>…</ca>` 等）。
  - 校验在 daemon 收下配置时做（M4-8 的增删接口回 422 并指出行号），agent 下发前再校验一次。
- **拍板 6**：status 的 `exits_down` 不保留兼容，直接删掉，换成按出口的可用状态（M4-8）。

**【v2.1】M4-7 的补充**（architect 判 M4-1 时给出）：

- **第 0 步：内核模块的软依赖**在 `internal/kmod` 的加载器里通用地支持：读 `modules.softdep` 的 `pre:`，加载目标模块前先尝试加载；软依赖失败只记日志、继续；去掉 M4-1 里手工先加载 `crc32c_generic` 的那一行，用探查重新验证。
- **OpenVPN 推送的 DNS**：只有它调用的脚本拿得到，而用户配置里的脚本类指令一律拒绝。由 agent 自己提供一个固定的脚本接收推送的选项（是我们的脚本，不是用户配置里的）；开工时评估具体方式写进计划；拿不到时退到固定的公共解析器，仍只经隧道。

**【v2.8】M4-7 的补充决定**（architect 2026-11-20 判 W-0 时给出；M4-7 一节和 v2、v2.1 的补充照做，再明确以下几点）：

1. **配置的解析和校验单独成包** `internal/exitconf`（纯计算，各平台都能编）：WireGuard、OpenVPN、订阅 mihomo 三种配置的指令白名单，以及取出服务器端点（地址或域名、端口、协议）的函数。daemon 在 M4-8 收下配置时用它，agent 下发前也用它，两边同一份规则。
2. **WireGuard 不用 `wg-quick`**（M4-1 的结论）：agent 自己建接口、配地址和路由，只调用 `wg setconf`；交给 `wg` 的配置文件只含它认识的那几项，由 agent 从校验过的结构重新生成，不把用户的原文交出去。
3. **OpenVPN**：命令行和配置由 agent 从校验过的结构重新生成；推送的 DNS 用 agent 自带的固定脚本接收（路径固定、内容随镜像，只把推送的 DNS 写到该出口自己的目录里）；拿不到时用固定的公共解析器，经隧道访问。
4. **每个出口的命名空间**沿用 M4-1 验证过的布局（veth 加根命名空间的 NAT，命名空间里的断网规则只放行到服务器端点）；命名空间里的 socks 服务解析域名只经隧道（v2 必须改 3）；断网规则把 53 端口也算进去。
5. **凭据**：只经控制面下发，落在内存文件系统里该出口自己的目录，权限只给 root；引擎停止或出口被删除时目录一并删除；请求体、配置内容、密钥不进任何日志，不出现在 health 和诊断接口里。
6. **出口的状态**：引擎在运行，并且（VPN 类）隧道接口存在；WireGuard 另看最近一次握手，超过 3 分钟没有握手算不可用；状态经 health 给出，不带端点地址。
7. **内核模块的软依赖**在加载器里通用支持（M4-1 时定的），本任务第 0 步做。
8. **本任务只做虚拟机里面的部分**，对端仍用同一个虚拟机里的另一个命名空间；出口的服务器在公网时虚拟机的出站白名单怎么放行它，属于 M4-8。

**验收（M4-7，v2.8）**：

- a. 第 0 步：软依赖的单测（有 `pre:` 的先加载；软依赖加载失败不算错；目标模块失败才报错；有环时不死循环）；M4-1 的探查在去掉手工加载之后重新跑通，证据写进 scripts/dev/out/。
- b. 配置校验（纯单测）：三种配置各有合法样本；WireGuard 的每个被禁指令各一例被拒并指出行号；OpenVPN 的脚本类、插件、管理接口、引用外部文件的指令各一例被拒；重新生成的配置里只有白名单内的指令，原文的注释和未知内容不会被带过去；端点提取：IP、域名、带端口、IPv6 端点（拒绝并说明暂不支持）各一例；模糊测试 60 秒不崩溃。
- c. 同机对端的端到端（真实虚拟机，证据写进 scripts/dev/out/）：经数据通道指定 WireGuard、OpenVPN、订阅 mihomo 三个出口，各做一次 TCP 回显和一次 UDP 回显，回显来自对应的对端；三个出口同时运行，并发各 50 条流，全部到达对应的对端。
- d. 隧道断开时不泄漏：对端一侧的计数显示该出口的命名空间只发出过到服务器端点的包；数据通道对该出口开流得到“出口不可用”，不改走别的路径；其他两个出口不受影响。
- e. 解析只经隧道：经出口访问一个域名时 53 端口的查询出现在隧道里（对端一侧计数）；根命名空间和 veth 上看不到该出口发出的查询；断开隧道后解析失败，没有任何查询从别处出去。
- f. 凭据：测试用的密钥只出现在内存文件系统里该出口的目录，权限正确；虚拟机的控制台日志、agent 日志、health、诊断接口的输出里搜不到；删除出口后目录消失；下发接口对不合法的配置返回错误，不留下半成品目录。
- g. 没有隐式直连（R20）：三种出口各自在正常和断开两种状态下，宿主一侧绑物理网卡的拨号数不增长。

**【v2.11】M4-8 的补充决定**（architect 2026-11-21 判 W-1 时给出；本节上面的内容照做，再明确以下几点；这 8 条即 M4-8 的实施计划）：

1. **出口的配置和凭据存在本机**：状态目录下的 `secrets/`，属主才能读写，原子写，一个出口一个文件。接口的读操作只回摘要：标签、类型、服务器端点的主机名或“已配置”字样、可用状态；永远不回配置原文和密钥。收下配置时用 `exitconf` 校验，不合法回 422 并指出行号。
2. **出口标签与规则的一致性**：规则里引用了不存在的出口，改规则时被拒并指出是哪一条；删除还被规则引用的出口回 409 并列出引用它的规则序号；出口的增删与启用、停用、恢复、改规则互斥，共用忙标记。
3. **下发给虚拟机的时机**：启用时；出口集合变化时；发现虚拟机重启过时（health 里的启动标识变了）。下发失败时该出口标为不可用、规则回退主代理、发事件；不影响主代理和闸门。
4. **服务器端点与宿主的出站白名单**（本任务里唯一碰“虚拟机能往哪里拨号”的地方）：各出口的引擎从宿主的物理网卡直接连到它的服务器（7.3 的本意：分流出口是独立的一条路，不经主代理），所以宿主的出站白名单要包含各出口的服务器端点。白名单在运行中更新，不靠重启虚拟机宿主（重启期间闸门会关、所有连接都断）：abroad-vm 自己的诊断接口上加“替换分流出口端点集合”的操作，只接受属主或 root 的调用（沿用对端身份校验），主代理第一跳的那部分白名单不受它影响。**端点是域名时**沿用 M2-1 的“第一跳域名由网关代解析”：把出口端点的域名加进允许代解析的名单，解析结果同时用于宿主的放行和虚拟机里该出口命名空间的断网规则，变化时两处一起更新；解析走宿主的系统解析路径、以专用用户的身份发出（和主代理第一跳的域名一样），不经主代理、不经别的出口。现有机制装不下这个用法（例如只支持启动时给定的名单）时停下来找 architect，不另造一套。端点的合法性：拒绝回环（开发用的同机对端除外，由开发标记控制）、组播、fake 段、Anthropic 地址段、IPv6。
5. **按出口的检查**：每个分流出口用 exitcheck 经它自己开流做检查（HTTPS 探测、UDP 探测、出口 IP 和大陆段）；不做基准比对、不做地区同步。结果进“按出口的可用状态”：明确不通过或大陆段 → 不可用、规则回退主代理；无法判断 → 沿用上一次的结论，最多 10 分钟；UDP 探测不通过 → 只把该出口的 UDP 回退主代理，TCP 照走它。检查和主代理的复查同一个循环，每轮在总时限内完成；出口多时分批，单个出口卡住不拖累主代理的续期。M3 留下的“开流失败后 30 秒不可用”保留为一个输入，检查结果是另一个输入，两者任一说不可用就不可用（取代本节上面“删除 `ExitDownFor`、`markExitDown`”的写法；status 的 `exits_down` 仍删掉，换成按出口的可用状态）。
6. **status**：按出口给出开流计数、可用状态、最近一次检查的各项结果；不含出口 IP、端点地址。

4. **环境检测**：启用后 17 项全部通过；人为制造泄漏（打开系统代理、给一个终端设 `HTTPS_PROXY` 后启动 `claude`、关掉 IPv6 关闭）能检出、闸门关闭，修好后重新放行。
5. **R7、R16**：停用状态下观察 APNs、时间同步；（有条件时）需要认证的 Wi-Fi。
6. 还原、采样。

交付：README、空跑证据、命令核对、自测。主会话不执行真机部分。

## 3. 四条底线由谁证明

| 底线 | 离线证明（会话里） | 真机证明（M4-9） |
|---|---|---|
| **不泄漏** | M4-3 d：主代理 Fail → 闸门全关（含走分流出口的流）；M4-7 b：隧道断开时出口命名空间只能连对端，数据面开流失败不改走直连；M4-7 e：每种出口没有隐式直连；M4-6 f：本机真实 IP 的测量经直连拨号模块、只在内存，STUN 目标不是 Claude 的域名（源码检查：envcheck 里直连只用于 STUN） | 第 2 步（真实 VPN 断开不泄漏）、第 4 步（人为泄漏能检出） |
| **失败即断网** | M4-3 a：复查协程卡死或崩溃时租约 90 秒到期自动关闭；多原因时任何一方都不能越权打开；M4-3 e：崩溃穷举加复查后仍成立；M4-6 c：Unknown 超过 10 分钟按不通过 | 第 4 步（打开系统代理 → 闸门关闭） |
| **不误杀** | M4-2 c、f：查询服务故障 → Unknown，单次网络错误不会变成 Fail；M4-3 b、c：Unknown 沿用 10 分钟、同国漂移不关闸门；M4-2 d、e：单次探测失败只影响该次结论；M4-6 c、d：警告项不阻断 | 第 4 步（正常环境下 17 项全部通过，没有误关） |
| **回国干净** | M4-5 a、b：崩溃穷举加地区步骤后原值不丢、恢复后逐项还原；M4-5 c：出口漂移不改地区；虚拟机内的地区只写虚拟机的文件（agent 的单测：只碰 `/etc/localtime`、`/etc/TZ`、`/etc/profile.d/locale.sh`）；M4-4 b：结束不了的进程会中止回国 | 第 1 步（R4：读回与原值一致）、第 3 步（Claude 进程被结束、地区还原） |
